## Bitcoin-Related Docker Images
This repository will be continuously maintained, but suggestions, comments, PRs are welcome!
This repository doesn't introduce anything novel, it just accumulates some Bitcoin-related, dockerized daemons/services.

Some simple HOW-TO-RUNs are included. Keep in mind that there have been some assumptions made by the way the HOW-TO-RUNs are defined (i.e. you need to have `/mnt/data/...` created, `bitcoin/lightning.conf` files, etc.). Feel free to make suggestions how to make the services even more generic and simpler to productionize. Also, if you don't want to run as a systemd service, just use the `docker run...` part with its respective options.

## Builds
* Changes to the respective `elementsd`, `bitcoind`, `lightningd` subdirectory will create a manual build job
* Edit the `VER` in the `build-and-push-to-dockerhub.sh` script to update the version
* If you also want to tag the Docker image with `:latest`, set the env variable `LATEST` to `1` before triggering the job

### Publishing to additional registries

With no additional settings, publishing uses the existing Docker Hub image names.
`PUBLISH_REPOSITORIES` is a space-separated list of repository prefixes; image
`<name>` is tagged as `<prefix>/<name>`. Include `blockstream` in that list to
retain Docker Hub alongside additional destinations. An unset value defaults to
`blockstream` (or the prefix of the existing image override). Each build runs
once with repeated tags, then verifies that every destination has the same index
digest, including its platforms and attestations.

| CI/CD variable | Requirement and behavior |
| --- | --- |
| `PUBLISH_REPOSITORIES` | Optional; repository prefixes as described above. |
| `PUBLISH_MIRRORS` | Optional; `false` restricts publishing and authentication to the original Docker Hub path and skips release copies. Defaults to enabled. |
| `DOCKERHUB_USER`, `DOCKERHUB_PW` | Existing Docker Hub login variables, required for authenticated publishing. |
| `MIRROR_REGISTRY`, `MIRROR_REGISTRY_USER`, `MIRROR_REGISTRY_PASSWORD` | Optional basic authentication; login occurs only when all three are set and the host is selected by `PUBLISH_REPOSITORIES`. |
| `GCP_ID_TOKEN_AUDIENCE` | Required only for a selected Google token registry; use the configured OIDC audience. YAML defaults to the harmless string `unset` so ordinary jobs do not have an empty audience. |
| `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT` | Required only for a selected Google token registry; configure the provider resource and service account in project CI/CD settings. |
| `GCP_ID_TOKEN` | Generated by GitLab `id_tokens`; do not store a long-lived token in project settings. |
| `PUSH` | Optional; `false` validates builds without publishing or registry login. Merge request jobs use this mode. Defaults to `true`. |
| `FORCE` | Optional; `1` explicitly permits replacing existing version tags. Defaults to `0`. |

Set registry usernames containing a literal `$` as **raw variables with expansion
disabled** in GitLab CI/CD settings. The login script expands the value once in
double quotes and passes passwords through standard input; no YAML variable
alias re-expands the username.

A selected Google-hosted Docker registry uses short-lived OAuth tokens through
GitLab OIDC and Google Workload Identity Federation. The identical
`google-token-login.sh` helper in each repository exchanges the job token with
Google STS, requests a service-account access token, and logs Docker in through
standard input. It uses `curl` and `jq` (installed with `apk` if absent), without
an SDK or an additional image. All identity configuration comes from CI/CD
variables. `GCP_STS_URL` and `GCP_IAMCREDENTIALS_URL` override endpoints **only for
local mock tests**; leave them unset in CI.

Publishing preflights every version tag before writing any destination. An
existing version is refused unless `FORCE=1`; release copies may reuse a tag
already pointing at the expected digest. Only explicit missing-manifest responses
count as absence: authentication, network and unexpected registry errors fail the
job. Existing `latest` and `latest-*` aliases remain mutable. These checks are
not an atomic registry lock; serialize publishers of the same version. A failed
push or digest check fails the job, and partial registry writes are not rolled
back automatically.

Existing build job names and image versions/platforms are retained. Changed image
jobs validate merge requests with `PUSH=false` for `linux/amd64` only; publishing jobs are manual and
master-only. Local scripts accept optional `PLATFORMS` to override the existing
platform list (for example `linux/amd64`). `LATEST=1` retains the opt-in latest
aliases for bitcoind, elementsd and lightningd; the other scripts retain their
existing tag choices and version/build-argument variables.
